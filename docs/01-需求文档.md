## 1. 项目背景与目标

### 1.1 背景

在线客服场景中，大量用户提问是重复的常见问题（怎么退货、运费谁出、怎么开发票）。全部由人工回答，成本高、响应慢；但完全自动化也不现实，因为总有一部分问题机器解决不了。

比较合理的做法是**人机协作、分层拦截**：

- 常见问题：自动查知识库，直接回答；
- 能看懂但知识库里没有准确答案的问题：列出相似问题，引导用户自助选择；
- 机器搞不定的问题：自动创建工单，按问题类型分配给对应部门，人工处理后按状态流转闭环。

### 1.2 项目目标

用 Python 实现一套演示级的智能客服工单系统，包含三个 Agent：

1. **意图识别 Agent**：判断用户问题属于 售后 / 咨询 / 投诉 / 其他，输出置信度；置信度低时兜底转人工。
2. **知识检索 Agent**：从知识库检索答案，能回答就直接回复；回答不了走降级方案。
3. **工单处理 Agent**：解决不了的自动创建工单、分配给对应部门，并管理工单状态机（待处理 → 处理中 → 已解决）。

项目定位是**面试展示项目**，因此额外强调：工程结构清晰、每一层都有异常降级策略、代码朴素可读（不炫技）。

### 1.3 成功标准

- 不配任何 API key（Mock 模式）时，全部业务流程可离线跑通；
- 接入真实 LLM 后，意图分类准确，低置信度问题正确转人工；
- 三条核心降级链路（意图兜底、检索降级、非法流转拦截）都可以现场演示；
- 一个命令启动服务，一个命令进入命令行演示。

## 2. 用户角色

| 角色 | 说明 | 使用方式 |
|---|---|---|
| 终端用户 | 提问题、等答复的人 | 命令行客户端 / REST API |
| 人工处理人 | 部门里接单、处理、解决工单的人 | REST API（工单管理接口） |
| 开发 / 演示者 | 跑 demo、讲解项目的人 | uv 命令 |

> 说明：本系统不做注册登录和权限体系（见第 6 节），"处理人"以提交请求时填写的姓名为准，属于演示级简化。

## 3. 核心业务场景

### 场景 1：知识库直接解决（最理想路径）

> 用户输入："怎么申请退货？"
> 意图识别 → 售后（after_sale），置信度 0.95
> 知识检索 → 命中知识条目"如何申请退货"，相似度 0.78
> 系统直接回复退货流程。**不创建工单。**

### 场景 2：知识库部分命中（检索降级）

> 用户输入："买的东西用了两天就坏了，能修吗？要钱吗？"
> 知识检索最高相似度 0.42，不够直接回答的标准
> 系统回复"没有找到完全匹配的答案，您想问的是不是以下问题？"，并列出最相似的 3 个问题
> - 用户选中某一条 → 回复该条答案，流程结束；
> - 用户回复"都不是" → 创建工单，转人工。

### 场景 3：投诉直接建单

> 用户输入："快递员把我的包裹扔坏了，我要投诉！"
> 意图识别 → 投诉（complaint），置信度 0.97
> 投诉不走知识库自动回答（投诉是情绪和责任问题，机器模板回复会激化矛盾），直接创建工单 → 客服质控组，状态"待处理"，并回复安抚话术 + 工单号。

### 场景 4：意图不明转人工（意图兜底）

> 用户输入："你们这什么破系统啊"
> 意图识别置信度 0.30，低于阈值 0.6
> 创建工单并标记"意图不明" → 综合受理组，回复转人工话术。

### 场景 5：工单流转（人工侧）

> 处理人查看"待处理"工单列表 → 接单（待处理 → 处理中）→ 填写解决方案并解决（处理中 → 已解决）。
> 如果对"待处理"的工单直接调用"解决"接口 → 系统拒绝，返回 400 和明确错误信息，并记录一条非法操作事件。

### 场景 6：LLM 不可用（服务降级）

> 网络异常 / 未配置 API key / LLM 服务超时 → 意图识别自动降级为关键词规则分类，全流程不中断；分类结果置信度标记为低值，倾向转人工。

## 4. 功能需求

优先级：P0 = 必须实现；P1 = 应该实现；P2 = 可以实现。

### 意图识别

**FR-1 意图识别（P0）**
- 输入：用户问题文本。
- 输出：意图（after_sale / consultation / complaint / other）+ 置信度（0~1）+ 一句话理由。
- 实现方式：通过 Prompt 约束 LLM 输出固定格式的 JSON。

**FR-2 意图识别兜底链（P0，亮点 1）**
- LLM 输出不是合法 JSON → 携带错误信息重试 1 次；
- 重试仍失败 → 使用关键词规则分类；
- LLM 调用异常（超时、网络错误）→ 跳过重试，直接使用关键词规则；
- 兜底结果置信度固定为低值（0.4），使其自然触发转人工；
- 置信度 < 0.6（可配置）→ 创建工单转人工，不再往下走。

### 知识检索

**FR-3 知识检索（P0）**
- 知识库为 JSON 文件（问题 + 答案 + 关键词）；
- 检索方式：jieba 分词 + TF-IDF + 余弦相似度；
- 最高相似度 ≥ 0.55 → 直接返回对应答案。

**FR-4 检索降级（P0，亮点 2）**
- 最高相似度在 0.30 ~ 0.55 之间 → 返回 top3 相似问题列表，让用户选择；
- 用户选中 → 回复该问题答案；用户放弃（回复"都不是"）→ 创建工单；
- 最高相似度 < 0.30 → 直接创建工单。

**FR-5 投诉直通工单（P0）**
- 意图为 complaint 时不查知识库，直接创建工单到客服质控组，回复安抚话术。

### 工单

**FR-6 工单创建（P0）**
- 工单号规则：`T + 日期 + 4 位当日序号`，如 `T20260823-0001`；
- 记录字段：原始问题、意图、置信度、分配部门、状态、创建/更新时间、处理人、解决方案；
- 部门按意图自动路由（路由表见设计文档）。

**FR-7 工单状态机（P0，亮点 3）**
- 状态：待处理（PENDING）→ 处理中（PROCESSING）→ 已解决（RESOLVED）；
- 只允许表中定义的合法流转；非法流转拒绝并报错；
- 每次状态变化（含非法尝试）写入事件流水表，可追溯。

**FR-8 工单管理（P0）**
- 按状态 / 部门筛选工单列表；
- 查看工单详情（含完整事件时间线）；
- 接单（待处理 → 处理中）、解决（处理中 → 已解决，需填写解决方案）。

### 接口与交互

**FR-9 对话接口（P0）**
- `POST /api/chat`：提交问题，返回路由结果（直接回答 / 相似问题列表 / 已建工单 / 已转人工）；
- `POST /api/chat/choose`：用户对相似问题列表做出选择（选某条 / 都不是）。

**FR-10 工单接口（P0）**
- 列表、详情、接单、解决四个接口（见设计文档）。

**FR-11 命令行演示客户端（P0）**
- 终端问答循环：输入问题 → 展示意图、置信度、路由结果；
- 相似问题列表以编号形式展示，输入编号选择，输入 0 表示"都不是"。

**FR-12 Mock 模式（P0）**
- `LLM_PROVIDER=mock` 时不调用真实 LLM，用关键词规则模拟，全流程离线可跑、测试可跑。

**FR-13 会话候选暂存（P0）**
- 服务端为每个会话（session_id）暂存上一次返回的候选问题，支撑 `/api/chat/choose`。

### 可维护性

**FR-14 知识库可维护（P1）**
- knowledge.json 支持增删改，重启服务后生效。

## 5. 非功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-1 | 可读性优先 | 代码朴素，完整单词命名，函数短小；不用高级语法炫技；注释只解释"为什么" |
| NFR-2 | 可配置 | 模型地址 / key / 模型名 / 各阈值 / 数据库路径，全部走 .env 配置 |
| NFR-3 | 可测试 | LLM 可 Mock；意图、检索、状态机、接口均有单元测试；测试不依赖网络 |
| NFR-4 | 性能 | Mock 模式下单次对话响应 < 100ms；真实 LLM 下 < 8s |
| NFR-5 | 零部署 | SQLite 单文件数据库，无额外中间件；知识库为 JSON 文件 |
| NFR-6 | 可观测 | 关键节点输出日志：意图结果、检索最高分、工单创建与流转 |

## 6. 范围外（明确不做）

- 多轮上下文对话（每问独立处理，仅相似问题选择这一个分支有会话状态）；
- 用户注册、登录、权限体系；
- 消息通知（邮件 / 短信提醒处理人）；
- 高并发、分布式部署；
- 知识库后台管理界面（直接编辑 JSON 文件）；
- 工单重新打开、升级、转派等扩展状态（设计文档中给出扩展方向）。

## 7. 验收标准（演示脚本）

1. `uv sync` 安装依赖，`uv run uvicorn app.main:app` 启动服务成功；
2. `uv run python scripts/chat_cli.py` 进入演示，依次输入四类问题，分别走到：
   - 知识库直接回答；
   - 相似问题列表（选择、放弃两个分支都走通）；
   - 投诉直接建单；
   - 低置信度转人工；
3. 工单接口演示：查询列表 → 接单 → 解决 → 查详情，事件时间线完整；
4. 对"待处理"工单直接调用解决接口，返回 400 和明确错误信息；
5. `LLM_PROVIDER=mock` 时，上述 1~4 全部通过；
6. `uv run pytest` 全部测试通过（测试全程不访问真实 LLM）。
