## 2. 开场：项目一分钟介绍

> "我做了一个智能客服工单系统，核心是人机协作分层拦截：用户提问进来，先由意图识别 Agent 判断是售后、咨询还是投诉；售后的常见问题直接查知识库回答；知识库答不了的，不硬答，返回相似问题让用户选；实在解决不了就自动创建工单，按意图分配给对应部门，走 待处理 → 处理中 → 已解决 的状态机闭环。技术栈是 Python + FastAPI + SQLite，大模型走 OpenAI 兼容接口，检索用 jieba 加 TF-IDF，全程 uv 管理环境。整个项目我特意做了三层降级设计：意图识别有四级兜底链，检索有三级阈值路由，工单有状态机合法性校验，每一层都保留'承认解决不了、转人工'的出口。"

介绍完再开始演示，顺序是：**先跑通最理想路径，再逐个演示降级路径**——从"系统很聪明"演到"系统很可靠"。

## 3. 演示脚本（按顺序执行）

### Step 0：启动服务

```bash
uv run uvicorn app.main:app --port 8000
```

另开终端：

```bash
uv run python scripts/chat_cli.py
```

> 顺带提一句："接口文档是 FastAPI 自动生成的，在 /docs 可以直接点着调。"

### Step 1：知识库直接回答（理想路径）

输入：`怎么申请退货？`

预期输出：意图 after_sale（置信度 0.9 左右）、路由 `kb_answer`、直接给出退货流程答案、显示命中的知识条目和相似度分数。

> 讲解话术："这是最理想的路径，知识库命中直接回答，不打扰人工。注意我这里会显示检索分数，TF-IDF 的结果是可解释的——能说清楚命中了哪些词，这是我不上向量库的原因之一。"

### Step 2：检索降级——相似问题列表（亮点 2）

输入：`买的东西用了两天就坏了，能修吗？要钱吗？`

预期输出：路由 `similar_questions`，列出 top3 相似问题（编号 1~3），提示"回复序号选择，回复 0 表示都不是"。

**分支 A（用户选）**：输入 `1` → 返回对应答案。
**分支 B（用户放弃）**：输入 `0` → 创建工单转人工，返回工单号和部门。

> 讲解话术："这条问题的最高相似度大概 0.4，在 0.30 到 0.55 之间。这个区间我定义为'不能直接回答'——宁可把相似问题摆出来让用户自己选，也不硬编一个答案，从机制上避免幻觉。用户选了就自助解决，选 0 就自动建单转人工，两条出路都是闭环。"

### Step 3：投诉直通建单（意图路由）

输入：`快递员把我的包裹扔坏了，我要投诉！`

预期输出：意图 complaint、不查知识库、直接创建工单到客服质控组、回复安抚话术 + 工单号。

> 讲解话术："投诉我特意设计成不走知识库。投诉背后是情绪和责任认定，机器拿模板话术回复只会激化矛盾，所以识别出来直接建单给质控组，让真人尽快介入。这是意图驱动的路由策略，不是所有问题都硬套同一个流程。"

### Step 4：低置信度转人工（亮点 1）

输入：`你们这什么破系统啊`

预期输出：置信度低于 0.6、意图 unknown、建工单到综合受理组、转人工话术。

> 讲解话术："这句话人都不好判断是投诉还是吐槽，模型置信度只有零点几。我的策略是置信度低于 0.6 一律不猜，建单转人工——宁可多转一次人工，不能错分。这个阈值在 .env 里可调，调高就更保守，调低就更激进。"

### Step 5：工单状态机流转（亮点 3）

用 curl 或 /docs 页面依次执行（工单号以上一步实际输出为准）：

```bash
# 看待处理工单列表（能看到前面几步建的单）
curl "http://127.0.0.1:8000/api/tickets?status=PENDING"

# 接单：待处理 -> 处理中
curl -X POST http://127.0.0.1:8000/api/tickets/T20260823-0003/assign \
  -H "Content-Type: application/json" -d '{"handler": "张三"}'

# 解决：处理中 -> 已解决
curl -X POST http://127.0.0.1:8000/api/tickets/T20260823-0003/resolve \
  -H "Content-Type: application/json" \
  -d '{"handler": "张三", "resolution": "已电话致歉并补发商品"}'

# 查详情：完整事件时间线
curl http://127.0.0.1:8000/api/tickets/T20260823-0003
```

预期输出：详情里的 events 按时间列出 created → assigned → resolved。

> 讲解话术："状态机只有三个状态、两条合法流转，全部集中定义在一张流转表里，是全系统唯一的合法依据，判断逻辑只有一处。每次流转都写事件流水，这张单子'谁在什么时候做了什么'全部可追溯。"

### Step 6：非法流转拦截（状态机的另一半）

对一张**待处理**（PENDING）的工单直接调用 resolve：

预期输出：HTTP 400，错误信息明确说明当前状态不允许该操作；查详情能看到一条 `invalid_attempt` 审计事件。

> 讲解话术："状态机价值的一半在'拒绝'。待处理的单子不允许直接解决，必须先有人接单——保证每张单都有明确承接人。非法操作不是静默失败，返回 400 的同时记审计事件。要扩展重开、转派，只是在流转表加一行，机制不变。"

### Step 7（可选）：Mock 模式展示工程解耦

```bash
# .env 里 LLM_PROVIDER 改为 mock 后重启
uv run pytest
```

> 讲解话术："LLM 是不可控外部依赖，所以我做了 Mock 实现和真实实现同接口，测试全程离线跑、稳定可重复——CI 里没有 key 也能跑。Mock 的规则和兜底链的关键词词典是同一份，保证两条链路行为一致。"

## 4. 翻车补救预案

| 现场问题 | 补救动作 | 观众感知 |
|---|---|---|
| LLM 接口超时 / 网络不通 | 说明"这正好演示兜底"，直接展示关键词兜底路径；或改 `LLM_PROVIDER=mock` 重启继续演 | 弱，甚至加分（本来就要讲降级） |
| 第 2 步话术没落进 0.30~0.55 区间 | 换预备话术重试；或现场调 `KB_MATCH_THRESHOLD` / `KB_SIMILAR_THRESHOLD` 讲阈值可配置 | 弱，顺势讲配置化 |
| 工单数据太乱 | 停服务、删 `tickets.db`、重启，一分钟重来 | 无感 |
| 端口被占用 | `--port 8001` 换端口 | 无感 |
| 完全没网 | 放提前录好的演示录屏 | 无感 |

## 5. 常见追问 Q&A

**Q1：为什么用 TF-IDF 不用向量检索 / RAG？**
> 知识库只有十几条，TF-IDF 零外部依赖、结果可解释（能说出命中了哪些词）、分数阈值好定。数据量上来或者口语化严重再上 embedding，检索模块接口不变，只换 kb.py 内部实现——架构上留好了这个口。

**Q2：置信度是模型自己打的分，靠谱吗？**
> 诚实说：是模型自评，不是校准概率。实测它对"问题清晰 / 模糊 / 无关"有区分度，做路由阈值够用。严格做法是多次采样投票或看 logits，我列为扩展项。关键是即使置信度失准，兜底方向是安全的——大不了多转几次人工，不会把错误答案硬塞给用户。

**Q3：为什么不用 LangChain / Agent 框架？**
> 三个 Agent 本质是三个职责单一的决策模块，pipeline 顺序编排就够了，引框架反而把简单流程包进黑盒，出问题难排查，依赖也重。自己写能讲清楚每一层怎么降级——这个项目的价值就在这些细节里。

**Q4：并发怎么办？**
> 演示级单进程：SQLite 加锁、工单号生成有 threading.Lock。真实场景换 PostgreSQL + 数据库序列或号段模式发号，会话暂存从内存 dict 换 Redis。架构不需要动，换的是实现。

**Q5：怎么支持多轮对话？**
> 现在每问独立，只有相似问题选择这一个分支有会话状态（内存暂存）。扩展：会话历史入库，意图识别的 Prompt 里带最近几轮；检索时把上一轮关键词并入查询。pipeline 结构不变。

**Q6：状态机为什么不允许回退 / 重开？**
> 本期从简，演示核心机制。真实客服系统会有 REOPEN（已解决 → 处理中），只需要在 ALLOWED_TRANSITIONS 加一行，机制完全不变——这正是集中式流转表的好处，扩展不动骨架。

**Q7：知识库怎么维护？**
> JSON 文件直接编辑，重启生效。下一步是命中统计：哪些问题检索分长期偏低，说明该补录知识了——让数据告诉你知识库缺什么。
