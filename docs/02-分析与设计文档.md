## 1. 总体架构

### 1.1 架构图

```
                        用户提问 (session_id, message)
                                  │
                                  ▼
                   ┌──────────────────────────┐
                   │       意图识别 Agent       │
                   │  LLM + Prompt 约束输出 JSON │
                   └─────────────┬────────────┘
              解析失败重试1次 │ 关键词规则兜底 │ 置信度 < 0.6
                 （兜底链见 2.4）│              │
                                 │              ▼
                 ┌───────────────┴────┐  ┌─────────────────────┐
                 │ 置信度 >= 0.6       │  │ 建工单（标记意图不明） │
                 └───────────────┬────┘  │ → 综合受理组，转人工   │
                                 │       └─────────────────────┘
              ┌──────────────────┼──────────────────┐
              │ complaint         │ after_sale / consultation │ other
              ▼                  ▼                           ▼
    ┌────────────────┐  ┌────────────────────┐    ┌──────────────────┐
    │ 投诉直通：建工单 │  │    知识检索 Agent     │    │ 建工单            │
    │ → 客服质控组     │  │ TF-IDF 余弦相似度    │    │ → 综合受理组       │
    │ + 安抚话术      │  └─────────┬──────────┘    └──────────────────┘
    └────────────────┘            │
              ┌───────────────────┼───────────────────┐
              │ 最高分 >= 0.55     │ 0.30 <= 最高分 < 0.55│ 最高分 < 0.30
              ▼                   ▼                    ▼
      ┌──────────────┐  ┌──────────────────┐   ┌──────────────┐
      │ 直接回复答案   │  │ 返回 top3 相似问题 │   │ 建工单        │
      │ (kb_answer)  │  │ 用户选择 / 都不是   │   │              │
      └──────────────┘  └────────┬─────────┘   └──────────────┘
                     选中→回复答案│ 放弃→建工单
                                  │
                                  ▼
                   ┌──────────────────────────┐
                   │       工单处理 Agent        │
                   │ 创建工单 → 按意图分配部门    │
                   │ 状态机：待处理→处理中→已解决 │
                   └──────────────────────────┘
```

### 1.2 一次请求的处理流程（编排层 pipeline）

1. 接收 `(session_id, message)`；
2. 调用意图识别 Agent，得到 `(intent, confidence)`；
3. `confidence < 0.6` → 创建工单（意图记为 unknown）→ 返回转人工话术；
4. `intent == complaint` → 创建工单到客服质控组 → 返回安抚话术 + 工单号；
5. `intent == other` → 创建工单到综合受理组 → 返回转人工话术；
6. `intent` 为售后/咨询 → 调用知识检索 Agent，按三级阈值路由（见 3.3）；
7. 任何需要建单的分支都调用工单处理 Agent，统一走建单 + 部门路由 + 初始状态 PENDING。

### 1.3 模块划分

| 模块 | 职责 |
|---|---|
| `app/agents/intent_agent.py` | 意图识别：构建 Prompt、调用 LLM、解析 JSON、兜底链 |
| `app/agents/retrieval_agent.py` | 知识检索：调用检索核心，按阈值输出三种路由结果 |
| `app/agents/ticket_agent.py` | 工单：创建、部门路由、状态机流转、查询 |
| `app/core/llm.py` | LLM 客户端：OpenAI 兼容实现 + Mock 实现 + 工厂函数 |
| `app/core/kb.py` | 知识库加载、分词、TF-IDF、相似度计算 |
| `app/core/store.py` | SQLite 访问：建表、工单 CRUD、工单号生成、事件写入 |
| `app/core/pipeline.py` | 编排：把三个 Agent 串成完整流程，管理会话候选暂存 |
| `app/main.py` | FastAPI 路由定义 |
| `scripts/chat_cli.py` | 命令行演示客户端 |

分层原则：**Agent 只做决策，core 只提供基础能力，pipeline 负责编排**。Agent 之间不互相调用，全部由 pipeline 串联，方便单测和替换。

### 1.4 意图路由策略表（核心决策表）

| 意图识别结果 | 后续动作 | 理由 |
|---|---|---|
| complaint（置信度达标） | 不查知识库，直接建工单 → 客服质控组，回复安抚话术 | 投诉包含情绪和责任认定，机器模板回复容易激化矛盾，必须人工介入 |
| after_sale / consultation | 查知识库，按三级阈值路由 | 这两类问题大多数有标准答案，最适合知识库拦截 |
| other（置信度达标） | 直接建工单 → 综合受理组 | 超出业务范围或无法归类，由人工判断 |
| 任意意图但置信度 < 0.6 | 建工单（意图记 unknown）→ 综合受理组，回复转人工话术 | 分类不可信时宁可转人工，不可错分（详见 2.5） |

## 2. 意图识别 Agent 设计

### 2.1 输入输出

```
输入:  question: str
输出:  IntentResult:
         intent: str        # after_sale / consultation / complaint / other / unknown
         confidence: float  # 0.0 ~ 1.0
         reason: str        # 一句话理由
         source: str        # llm / llm_retry / keyword_fallback（标记结果来源，便于演示和排查）
```

### 2.2 Prompt 设计（全文）

```
你是一个客服系统的意图分类器。请判断用户问题的类型，只输出一个 JSON 对象，不要输出任何其他内容。

意图类型只能是以下四种之一：
- after_sale：售后问题（退货、退款、换货、维修、物流异常、发票等）
- consultation：咨询问题（产品功能、使用方法、政策说明等）
- complaint：投诉（表达不满、明确要求投诉、服务质量差等）
- other：其他（与客服业务无关，或无法归入以上三类）

输出格式：
{"intent": "意图类型", "confidence": 0到1之间的小数, "reason": "一句话理由"}

示例：
用户：怎么申请退货？
输出：{"intent": "after_sale", "confidence": 0.95, "reason": "询问退货流程"}

用户：你们快递员态度太差了，我要投诉！
输出：{"intent": "complaint", "confidence": 0.97, "reason": "明确表达投诉意愿"}

用户：今天天气怎么样？
输出：{"intent": "other", "confidence": 0.90, "reason": "与客服业务无关"}

用户的问题是：{question}
输出：
```

设计要点：

| 手段 | 目的 |
|---|---|
| 枚举约束（"只能是以下四种之一"） | 收窄输出空间，杜绝模型自创类别 |
| few-shot 示例（含 other 反例） | 让模型学会边界判断，特别是"无关问题归 other" |
| "只输出一个 JSON 对象" | 便于程序解析；配合 2.4 的解析失败重试 |
| confidence 字段 | 模型自评置信度，作为兜底路由的依据 |

关于置信度的诚实说明：这是模型自评分数，不是校准过的概率。但实践中它对"问题清晰/问题模糊/与业务无关"有区分度，作为路由阈值够用；更严格的做法是接 logits 或多次采样投票，属于扩展方向（见 2.6）。

### 2.3 解析与校验

- 从返回文本中截取第一个 `{` 到最后一个 `}` 之间的内容，`json.loads` 解析（容忍模型在 JSON 外多说的话）；
- 校验：`intent` 必须在枚举内，`confidence` 必须是 0~1 之间的数；
- 任一校验不通过 → 视为解析失败，进入兜底链。

### 2.4 兜底链（亮点 1 的核心）

```
调用 LLM
   │
   ├─ 返回合法 JSON 且校验通过 ────────────► 使用该结果 (source=llm)
   │
   ├─ 解析/校验失败 ──► 把错误信息拼进 Prompt 重试 1 次
   │                       ├─ 成功 ─────────► 使用该结果 (source=llm_retry)
   │                       └─ 仍失败 ───────► 关键词规则 (source=keyword_fallback)
   │
   └─ 调用异常（超时/网络/未配 key）────────► 直接关键词规则，不重试 (source=keyword_fallback)
```

关键词规则词典（按优先级依次匹配，命中即停）：

| 意图 | 关键词 |
|---|---|
| after_sale | 退货、退款、退钱、换货、维修、售后、快递、物流、发货、破损、坏了、发票 |
| complaint | 投诉、举报、差评、态度、欺骗、欺诈、离谱、垃圾 |
| consultation | 怎么、如何、什么、为什么、能不能、可不、请问、多少 |
| other | 以上都不命中时的兜底 |

关键设计：**兜底结果的置信度固定为 0.4**（低于 0.6 阈值），即规则兜底出来的分类"默认不被信任"，会走转人工。理由：兜底触发本身说明 LLM 已经不可用，此时宁可保守，也不能把一个可能错误的分类继续往下传。

> 面试话术：LLM 的输出是不可控的外部依赖，我的原则是"每一步都可能失败，每一步失败都有下一个出口，最后一个出口是转人工"。

### 2.5 阈值说明

`INTENT_CONFIDENCE_THRESHOLD = 0.6`，经验初值，通过 .env 可调：

- 调高（如 0.8）：转人工更频繁，用户体验偏保守；
- 调低（如 0.4）：自动处理更多，但错分风险上升。

演示时可用边界案例（如"你们这什么破系统啊"）展示阈值生效。

### 2.6 扩展方向（不在本期范围）

- 多次采样投票估计置信度；
- 用小模型微调分类头替代 Prompt 分类；
- 意图层级细化（售后下分退货/维修/物流）。

## 3. 知识检索 Agent 设计

### 3.1 知识库格式

`app/data/knowledge.json`，数组，每条一个知识点：

```json
[
  {
    "id": 1,
    "category": "after_sale",
    "question": "如何申请退货",
    "answer": "签收后7天内，在「我的订单」中点击「申请退货」，选择退货原因，审核通过后寄回商品即可。运费：质量问题由我们承担，无理由退货运费自理。",
    "keywords": ["退货", "退款", "七天无理由"]
  },
  {
    "id": 5,
    "category": "consultation",
    "question": "支持哪些支付方式",
    "answer": "目前支持微信支付、支付宝、银行卡和货到付款。",
    "keywords": ["支付", "付款"]
  }
]
```

初版准备 12~15 条，覆盖售后（退货/换货/维修）、物流（查询/时效）、账户（改手机号/注销）、支付四类。`keywords` 参与检索打分（与 question 拼接后分词），用于弥补问题表述单一。

### 3.2 TF-IDF 检索流程

**建库（服务启动时一次）：**

1. 每条知识的检索文本 = `question + keywords` 拼接；
2. jieba 分词，去停用词（的、了、我、你们、吗、呢、能、可以 等）和单字符噪声词；
3. 统计每个词出现在多少条知识里（文档频率 df），计算 `idf = log(N / (1 + df))`（+1 平滑，避免除零）；
4. 每条知识表示为一个 TF-IDF 向量（tf 取词频，简单计数即可）。

**查询（每次提问）：**

1. 用户问题同样分词、去停用词；
2. 构建查询的 TF-IDF 向量（查询中没有的维度为 0）；
3. 与每条知识的向量算余弦相似度，按分数降序排列；
4. 取最高分进入阈值路由。

选型理由（面试可讲）：知识库只有十几条，TF-IDF 零外部依赖、逻辑透明、结果可解释（能直接说出"命中了哪些词"）；数据量大或口语化严重时再升级 embedding 检索，接口不变、只换 `kb.py` 内部实现。

### 3.3 三级阈值路由（亮点 2 的核心）

| 最高相似度 | 路由结果 | 用户看到 |
|---|---|---|
| ≥ 0.55（`KB_MATCH_THRESHOLD`） | `kb_answer` | 直接答案 |
| 0.30 ~ 0.55（`KB_SIMILAR_THRESHOLD`） | `similar_questions` | "没找到完全匹配的答案，您想问的是不是以下问题？" + top3 列表 |
| < 0.30 | 建工单 | 转人工话术 + 工单号 |

设计思想：**检索层绝不"硬答"**。分数不够就不生成/不复述答案，宁可降级。这从机制上避免了"检索到不相关内容也编一个回答"的幻觉问题。整个系统每层都有"承认解决不了"的出口，这是可靠性设计的核心。

### 3.4 相似问题交互与会话暂存

- 返回候选问题时，服务端在**内存字典**中记录：`session_id → [(question_id, question), ...]`；
- `POST /api/chat/choose`：
  - `question_id` 命中暂存列表 → 回复该条答案，清除暂存；
  - `question_id` 为空 → 用户放弃 → 创建工单，清除暂存；
  - 会话没有暂存记录或 id 不在列表中 → 返回 400（无效选择）。

演示级简化声明：暂存放内存，重启丢失、仅单进程有效；正式做法应放 Redis 或数据库并加过期时间。这是明确的取舍，不是疏忽。

### 3.5 扩展方向（不在本期范围）

- embedding 语义检索（与 TF-IDF 两级混合：关键词失败 → 语义兜底）；
- 检索结果缓存；
- 知识库命中统计，指导补录知识。

## 4. 工单处理 Agent 设计

### 4.1 部门路由表

| 意图 | 分配部门 |
|---|---|
| after_sale | 售后服务部 |
| complaint | 客服质控组 |
| consultation | 在线客服组 |
| other / unknown | 综合受理组 |

路由在创建工单时一次性完成，后续不自动改派（转派属于扩展功能）。

### 4.2 工单字段

| 字段 | 类型 | 说明 |
|---|---|---|
| ticket_id | TEXT 主键 | `TyyyyMMdd-xxxx`，如 `T20260823-0001` |
| session_id | TEXT | 创建该工单的会话 |
| question | TEXT | 用户原始问题 |
| intent | TEXT | 意图标签；意图不明时为 `unknown` |
| confidence | REAL | 意图识别置信度；关键词兜底/unknown 时为兜底值 |
| department | TEXT | 分配部门 |
| status | TEXT | PENDING / PROCESSING / RESOLVED |
| handler | TEXT | 处理人姓名，接单时写入 |
| resolution | TEXT | 解决方案，解决时必填 |
| created_at / updated_at | TEXT | ISO 格式时间 |

### 4.3 状态机（亮点 3 的核心）

```
                  接单 assign                     解决 resolve（必填解决方案）
   ┌──────────┐ ─────────────► ┌───────────┐ ──────────────────────────► ┌──────────┐
   │  待处理   │                │   处理中   │                              │  已解决   │
   │ PENDING  │                │PROCESSING │                              │ RESOLVED │
   └──────────┘                └───────────┘                              └──────────┘
```

流转表（系统唯一的流转依据）：

| 当前状态 | 动作 | 目标状态 | 动作语义 |
|---|---|---|---|
| PENDING | assign | PROCESSING | 处理人接单，开始处理 |
| PROCESSING | resolve | RESOLVED | 填写解决方案，问题闭环 |

设计要点：

1. **不允许跳过"处理中"直接解决**（PENDING → RESOLVED 是非法流转）：保证每张工单都有明确的承接人，责任可追溯；
2. **不允许回退**（已解决不能重新打开）：本期从简；正式系统会加 REOPEN（已解决 → 处理中），只需在流转表中加一行，机制不变——这是集中式流转表的好处；
3. **流转表集中定义**：`ALLOWED_TRANSITIONS` 字典是全系统唯一的合法流转依据，判断逻辑只有一处，不会散落各处的 if-else；
4. **非法流转处理**：抛出 `InvalidTransition` 异常 → API 层转成 400 返回，同时向事件表写入一条 `invalid_attempt` 事件（谁、何时、想做什么），可审计。

### 4.4 事件流水（审计）

`ticket_events` 表记录工单的全部动作：

| action | 触发时机 | detail 内容 |
|---|---|---|
| created | 建单 | 意图、置信度、分配部门 |
| assigned | 接单 | 处理人姓名 |
| resolved | 解决 | 解决方案 |
| invalid_attempt | 非法流转被拒绝 | 尝试的动作、当时的处理人 |

查看工单详情时返回完整事件时间线，回答"这张工单经历了什么"。

### 4.5 工单号生成

`T + 当天日期 + 当日 4 位序号`。查库取当日最大序号 +1；单进程内用 `threading.Lock` 保证并发下不重号（演示级足够，分布式场景需数据库序列或号段模式）。

## 5. 数据存储设计

### 5.1 SQLite 表结构（DDL）

```sql
CREATE TABLE IF NOT EXISTS tickets (
    ticket_id   TEXT PRIMARY KEY,
    session_id  TEXT NOT NULL,
    question    TEXT NOT NULL,
    intent      TEXT NOT NULL,
    confidence  REAL NOT NULL,
    department  TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'PENDING',
    handler     TEXT NOT NULL DEFAULT '',
    resolution  TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS ticket_events (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id  TEXT NOT NULL,
    action     TEXT NOT NULL,
    detail     TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
```

使用标准库 `sqlite3` 直连，不用 ORM：表就两张、查询简单，裸 SQL 更直观，也符合"语法朴素"的项目定位。

### 5.2 知识库 JSON

见 3.1。文件路径由 `KB_PATH` 配置，默认 `app/data/knowledge.json`。

### 5.3 会话候选暂存

`dict[str, list[dict]]`，进程内存，见 3.4。

## 6. 接口设计

统一约定：成功返回业务 JSON + HTTP 200；错误用 HTTP 状态码 + `{"detail": "错误说明"}`（FastAPI 默认风格，不额外包一层 code/msg）。

### 6.1 POST /api/chat —— 提交问题

请求：

```json
{ "session_id": "s-001", "message": "怎么申请退货？" }
```

响应按路由结果分四种：

```json
// 1. 知识库直接回答
{
  "route": "kb_answer",
  "intent": "after_sale", "confidence": 0.95, "intent_source": "llm",
  "reply": "签收后7天内，在「我的订单」中点击「申请退货」……",
  "matched_question": "如何申请退货", "score": 0.78
}

// 2. 返回相似问题列表
{
  "route": "similar_questions",
  "intent": "after_sale", "confidence": 0.9, "intent_source": "llm",
  "reply": "没有找到完全匹配的答案，您想问的是不是以下问题？回复序号选择，回复 0 表示都不是。",
  "similar_questions": [
    { "question_id": 3, "question": "商品坏了怎么维修" },
    { "question_id": 1, "question": "如何申请退货" },
    { "question_id": 6, "question": "退货运费谁承担" }
  ]
}

// 3. 已创建工单（投诉直通 / 检索未命中 / 用户放弃选择 / other）
{
  "route": "ticket_created",
  "intent": "complaint", "confidence": 0.97, "intent_source": "llm",
```

### 6.2 POST /api/chat/choose —— 用户选择相似问题

请求：

### 6.7 错误码

| 状态码 | 场景 |
|---|---|
| 400 | 非法状态流转 / 无效的问题选择 / 参数缺失 |
| 404 | 工单不存在 |
| 502 | LLM 完全不可用且兜底也失败（理论上兜底永不失败，此为最后防线） |

## 8. 降级与异常策略汇总（三大量换点总表）

| 层 | 触发场景 | 策略 | 用户感受 |
|---|---|---|---|
| 意图层 | LLM 输出非合法 JSON | 错误信息拼回 Prompt，重试 1 次 | 无感 |
| 意图层 | 重试仍解析失败 | 关键词规则分类，置信度记 0.4 | 倾向转人工 |
| 意图层 | LLM 调用异常（超时/网络/无 key） | 不重试，直接关键词规则 | 流程不中断，倾向转人工 |
| 意图层 | 置信度 < 0.6 | 建工单（unknown）转综合受理组 | 转人工话术 + 工单号 |
| 检索层 | 0.30 ≤ 最高分 < 0.55 | 返回 top3 相似问题供选择 | 选择列表 |
| 检索层 | 用户放弃选择 | 建工单 | 转人工话术 + 工单号 |
| 检索层 | 最高分 < 0.30 | 直接建工单 | 转人工话术 + 工单号 |
| 工单层 | 非法状态流转 | 拒绝执行 + 400 + 记 invalid_attempt 事件 | 明确报错，操作可审计 |

一句话原则：**每一层都保留"承认解决不了"的出口，出口的尽头是人工，绝不硬答、绝不静默失败。**

## 9. 简化与取舍声明（面试主动讲）

| 简化点 | 原因 | 正式系统的做法 |
|---|---|---|
| 会话候选暂存放内存 | 单机演示，重启可接受 | Redis + 过期时间 |
| API 无鉴权 | 演示项目 | token / 网关鉴权 |
| SQLite 单文件 | 零部署、够用 | MySQL / PostgreSQL |
| 无多轮上下文 | 场景以单问为主 | 会话历史入库，Prompt 带上下文 |
| 状态机无回退/重开 | 流转机制演示为主 | 流转表加 REOPEN 等条目即可，机制不变 |
